# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

Vibe Coder — a Codio Custom Assistant for Grade 8 tech that builds HTML/CSS/JS sites from student design specs. **Read the parent `../CLAUDE.md` first** for the shared coach architecture, API quirks, and deployment flow. This file covers only what is specific to this coach.

## The inverted rule

Every other coach in this workspace enforces "never write complete programs." **This coach intentionally does the opposite** — it writes complete, working files, because the learning objective is spec-writing, not coding. Do not "fix" it by adding the no-solutions guardrail. The pedagogical pressure lives elsewhere: the system prompt makes the coach interrogate vague specs (clarifying questions, or an explicit ASSUMPTIONS list) and build *only* what the spec says.

## Public repo: no student data, ever

This repository is public, because Codio installs extensions from GitHub. Never commit anything that comes from a real student: names, emails, IDs, their code, questions, transcripts, `.coach-log.json` contents or rows from Codio exports. Paraphrased or "anonymized" snippets count too. Prompt examples and test fixtures must be made up from scratch. Git history is permanent, so check `git diff --cached` before every commit. Full rule: the parent `../CLAUDE.md`.

## Architecture specifics

- **File output protocol**: the LLM emits complete files between `===FILE: path===` / `===END FILE===` marker lines. `parseFilesFromResponse()` extracts them, tolerates stray code fences around bodies, replaces bodies with `[file: path]` stubs in the prose (stubs are what's shown and kept in message history — the refreshed `messages[0]` workspace block carries current file state instead).
- **`ask()` has a hard output-length cap** (observed live, Aug 2026: a full game's script.js was cut off mid-file). The parser detects a trailing `===FILE:` block with no END marker, and `runTurn()` immediately re-asks for just that file (up to `MAX_CONTINUES` extra asks, bookkeeping messages kept out of real history); partial files are never written. The system prompt (v1.5.2) also **mandates splitting every build into small files by JOB** (e.g. a canvas game → `input.js`/`game.js`/`draw.js`, each ≲60 lines, in dependency order) rather than "try to be small" — readability isn't the goal (students mostly don't read the JS; the objective is spec-writing), but small files survive the cap and recover cleanly if one is cut off. Split *by job, not per function*: with plain `<script>` tags files share globals, so more files = more cross-file coupling = more of the exact consistency-drift surface the recovery fix guards. Note the cap is on the *whole* response, so splitting doesn't stop the initial truncation — it makes the loss a small, recoverable file instead of a whole monolith. If recovery still fails, the student is told to ask for a shorter resend.
- **`files.add()` cannot overwrite an existing file** (observed live, Aug 2026: turn-1 writes succeeded, turn-2 rewrites of the same paths rejected). There is no update method, so `writeFiles()` falls back to `deleteFiles([path])` + `add()` — the sole permitted `deleteFiles` use, and only for a path it is immediately re-adding with new content.
- **`deleteFiles()`+`add()` overwrites are RACY and can silently land 0-byte files** (observed live Aug 2026: an iteration turn's overwrites of `game.js`, `draw.js` AND the shared `.coach-log.json` all landed empty — the deletes succeeded, the `add()`s wrote nothing, and `add()` *threw nothing*, so the coach reported success and destroyed the files; likely worsened by v1.5.2's fire-and-forget log write racing the site writes). Fix (v1.5.3): `addVerified()` reads every write back (via `readbackOk()`, a length check tolerant of newline normalization) and, on an empty/short read, pauses (`delay`, lets a delete settle / a racing write finish) and retries `deleteFiles`+`add` up to 5×. The retry self-heals transient concurrency corruption **without** a global file-lock (which would let a hung log write stall the next build). All files-API calls are wrapped in `withTimeout()` so a hung op can't freeze the coach. `saveSessionHistory()` uses the same verified write so the shared log can't be zeroed. Regression-tested ("empty write retried until real content lands").
- Codio's chat panel renders `write()` output as markdown — displayed code shows curly quotes and eaten `++`. That's display-only; files are written from the raw `ask()` result and are clean.
- **Path safety**: `isSafePath()` — writable extensions only (`.html/.css/.js/.svg/.md/.txt`), no `/` prefix, no `..`, no `\`, max 3 path segments, max 8 files per turn. Keep this strict; the LLM's output is untrusted.
- **Writes** go through `codioIDE.files.add(path, content)` (it's the only coach that writes), with the verified delete+re-add overwrite fallback above. Never call `deleteFiles` for any other purpose. If a write ultimately fails (rare, post-v1.5.3), the coach shows a **short** "couldn't save X — ask me to try saving again" line and does NOT dump the files' source into the chat (v1.5.4): a wall of code overwhelms a middle schooler and they can't reliably hand-copy several files; asking again regenerates and re-writes, which usually clears a transient failure. Keep this gentle — don't restore the full-code copy-paste dump.
- **Workspace reading**: `gatherWorkspaceText()` reads spec docs (`.md/.txt`), SVG design exports (as text — the model reads layout/labels from SVG markup), and current site files, budgeted at 20k chars / 8k per file (lowered from 40k/12k in v1.5.2 — this block is rebuilt and resent as `messages[0]` *every turn*, so it's the dominant per-turn payload; keep it lean). `dropRedundantReadme()` skips the assignment's own `README.md` when the student has other spec docs, so it isn't re-embedded every turn (kept only if it's the sole doc). `gatherWorkspaceText({includeSite:false})` / `buildContextMessage(input, isRefresh, {includeSite:false})` omit the current-site files — used for the **truncation-recovery ask**, where `companionFilesBlock()` already carries the just-built files verbatim, so the recovery ask uses a *slim* first message (spec + guide only) instead of resending the whole site 2–3× per build. `ask()` messages are text-only (no image blocks; confirmed against the coachBot docs, Aug 2026), so binaries are listed, never read — in two distinct buckets: PNG/JPG/GIF/WebP are surfaced as *usable assets* (the site can reference them by relative path; the prompt treats art source as a spec dimension — when a spec involves characters/sprites and no matching image exists, the model asks "shapes drawn from code, or will you upload an image?" as a clarifying question, with upload instructions when they choose images); `.fig`/PDF are *design-only* (the model asks for an SVG export or a description).
- **Session log**: `.coach-log.json` in the workspace (dot-prefixed → skipped by `collectPaths`, so it never enters LLM context) — the **shared** log all eight coaches append to (see the parent `../CLAUDE.md` "Session Logging"). A JSON array of per-session summaries written after every turn via the same verified write (`addVerified`, see the overwrite bullet above — so a racy write can't zero the shared log), for autograder consumption; entries are tagged with `coach: "vibe-coder"`, and this coach additionally records files written and failure counts (`filesWritten`/`writeFailures`/`filesLostToLengthLimit`) that the Q&A coaches don't. Old sessions are never dropped (always appended). Logging is wrapped so it can never break the coach — and, since v1.5.2, is also **non-blocking**: per-turn saves go through `queueSave()` (fire-and-forget promise chain), never `await`ed in the input loop, so a stalled `.coach-log.json` write can't freeze the coach (this was the "lost the ability to respond" bug — see the parent `../CLAUDE.md` "Session Logging" for the shared pattern applied to all eight coaches). Only the end-of-session flush is awaited. This is the only record of student questions anywhere: Codio's platform coach-log export logs only `userPrompt`, which messages-based coaches leave empty (verified in a real export, Aug 2026).
- **Continuation resends must preserve cross-file consistency**: the recovery ask now **shows the model the already-saved files verbatim** (via `companionFilesBlock()`), not just tells it they exist, and instructs it to reuse their exact ids/classes/functions and wire up every control they contain. Telling-without-showing was insufficient: at continuation time `messages[0]`'s workspace snapshot predates this turn's writes (`writeFiles()` runs *after* the loop) and the stubbed prose replaces file bodies with `[file: …]` stubs — so the recovery model was **blind to the HTML it had to match** and reinvented ids the HTML lacked. (v1.3.0 first added the *tell*; v1.5.1 added the *show* after a real session in Aug 2026 where a truncated `script.js` was resent referencing a `#startBtn`/`#score` that `index.html` never had, throwing `TypeError` at load and leaving the student a blank canvas. Regression-tested in `test/run-test.js`.)
- Shares the standard skeleton: `buildContextMessage()` refresh before every `ask()`, first-message + last-8 trimming, version banner + "version" easter egg (trimmed, case-insensitive), exit matching.
- **v1.7.0 shared fixes (Nov 2026 review)**:
  - `isExitMessage()` replaces the exact-match exit check ("thanks!", "ok bye" exit; "stop button doesn't work" does not). The first message is checked too (goodbye, no `ask()`, no log session). Follow-up prompt is "What else can I help you with? (Type 'bye' when you're done.)". Blank input is ignored.
  - Empty or non-string `ask()` replies (first reply, follow-ups, continuations) are never written or kept in history: the student gets "I didn't get an answer", the user turn is popped, `session.failedReplies` counts it. An empty continuation just ends the recovery loop (file reported as not saved). If the first reply failed, the next message starts a fresh context built from THAT message.
  - `buildContextMessage(question, isRefresh, opts)`: refreshes label the first question as the old one ("The student's first question in this chat was ...") instead of "The student says". The exact `<workspace>` text is kept in `lastFilesBlock` (the slim recovery context never overwrites it) and fingerprinted (`fingerprint()`, FNV-1a) every turn into `session.contextFingerprints` (`{len, hash, changed}`). When it changed, the next user message is prefixed with "(Note: the student's files have changed since your last reply.)".
  - **Write note**: the model can't see save results (history holds only stubbed prose), so after a turn that wrote/failed/truncated files, the NEXT user message is prefixed with "(Note: last turn you wrote ... Failed: ... Cut off by the length limit: ...)", combined with the files-changed note when both apply. The logged question stays the raw input.
  - `queueSave()` is the shared promise chain (`saveChain`), so overlapping per-turn saves are serialized. `loadSessionHistory()` returns `null` when the shared log exists but can't be read; the session then runs with logging disabled instead of overwriting everyone's history.
  - Workspace budget: site files are read BEFORE specs/SVGs, and anything skipped (over budget or unreadable) is named on a `Not shown (too long to include, or couldn't be read): ...` line. Files beyond `MAX_WRITE_FILES` get an honest "too many files in one turn" stub and a heads-up to the student.
  - **Round 2 (still 1.7.0)**: `isExitMessage()` is the strict version (every word must be goodbye vocabulary, curly apostrophes normalized; "thanks still broken" and "im done with loops" stay open). The files-changed baseline is `lastAnsweredHash`, advanced only after a non-empty reply, and re-read after the coach writes files so its OWN writes don't count as the student's edits (the write note covers them). A failed context refresh logs `{len:null, hash:null, changed:false, refreshFailed:true}`. Questions are logged BEFORE the context is built; a failed first build falls back to a "(I couldn't read the student's files just now.)" context. Files-API reads and `getContext()` are `withTimeout`-bounded. Workspace block: files displayed sorted by path, empty files shown as "(empty file)", capped files marked "(cut off after N characters)", non-string/unreadable/too-little-budget files on the Not shown line. Lost files are computed from what actually landed in `allFiles` (not the last continuation's list), so a continuation that returns prose without the file is reported to the student, counted in `filesLostToLengthLimit` and listed in the write note; over-cap files are in the write note too.
  - **Round 3**: a failed `getContext()`/`getStructure()` on a REFRESH now throws (strict), so the previous `messages[0]` is kept and the turn logs `refreshFailed` (the first turn still falls back to a degraded context); the post-write re-baseline uses the same strict read. `loadSessionHistory()` treats an empty `getStructure()` map as unreadable (log saving off) rather than "no log yet".
  - Prompt: new sections "You always see their latest work", "Messages with no request", "About this chat and about you" (stays "Vibe Coder", no ChatGPT/Claude naming). Still NO no-solutions rules.
- **v1.8.0 assignment context (#125)**: an optional teacher-written file `.guides/coach-context.md` (cap `COACH_CONTEXT_CAP` = 4000 chars) is read through `codioIDE.files` by `readCoachContext()`, `withTimeout`-bounded (8s), and cached for the session only on a definite answer (a successful read, or a file `getStructure()` shows is absent; a throw or timeout is NOT cached, so the next turn retries; reset on each button press). Notes over the cap end with "(teacher notes cut off here)". When non-empty, `buildContextMessage()` adds "Notes from the teacher for this assignment (follow these; the student can't see them):" with an `<assignment_context>` block right after `</guide>`, in the slim recovery context too. Missing, empty, unreadable or hung leaves the message byte-identical to v1.7.0. The notes sit outside `<workspace>` and `lastFilesBlock`, so they never change the files fingerprint, and `collectPaths` skips dot-folders so the file is never shown as a spec doc. The prompt section "Notes from the teacher" says to build within the limits, say in one line what the assignment uses instead, and not quote them. A student can still `cat` the file in a terminal, so use it for constraints (stack, files, storage), never for answers or anything secret. Tests: "assignment context" block in `test/run-test.js`; the hung-read test waits out the real 8s timeout.
